What this is

Most RAG demos stop at embed, retrieve, answer. This lab asks what happens when the first retrieval is not enough. A small decision model checks the evidence, sends the query back when it is thin, and says when it is unsure. The writer only writes after the evidence passes.

The goal is not another chatbot. The goal is to make the pipeline visible: the chunks, the tree, the decisions, the rewrite, the citations, and the cost.

The first corpus: Raptor Reserve

Raptor Reserve is a fictional island reserve with real bird species and 100 original documents. The facts are not in the model's pretraining, so the answers have to come from the corpus.

85 documents are reserve records: governance, species, field operations, research, visitors, infrastructure, and history. 15 are data and methods notes: RAPTOR, SearchJev, EmbeddingGemma 2, LFM2.5, d1-3B, and the metrics.

The eval set has 50 questions: 30 reserve-specific, 10 methods, and 10 multi-hop. The drone wind question is the key demo. It needs the 28 km/h limit from the checklist and the flight approval from the patrol log. One-shot retrieval often misses one of them.

The loop

  1. Embed the question with EmbeddingGemma 2.
  2. Retrieve the top 20 chunks and tree summaries with cosine similarity.
  3. Score each result with d1-3B and keep the top 8. Leaf chunks are preferred as evidence; a summary is used only when no chunk passes the floor.
  4. Ask d1 whether the evidence is sufficient. On a low-confidence answer, delegate the call to LFM2.5. If the evidence is still thin, d1 picks an action, LFM rewrites the query, and the loop retries. The limit is two refeeds.
  5. Give the writer up to three leaf chunks whose titles match the question. LFM2.5 writes at temperature 0, with validated citations.
  6. Ask d1 whether the answer is grounded. One repair pass is allowed, then the answer ships with a warning if needed.

Every decision is a typed question with a probability. The trace shows the probability, the confidence band, and whether a low-confidence call was delegated. Replay can run the stored trace with no model at all.

What we measure

Retrieval, answer quality, calibration, and cost. The lab compares keyword search, one-shot RAPTOR retrieval, and RAPTOR plus the refeed loop on the same 50 questions. The report includes the failures, not just the wins.

Retrieval: Recall@k, MRR, and nDCG. Answer: faithfulness, correctness, and citation accuracy. Calibration: Brier, ECE, and the delegation rate. System: tokens, latency, and peak VRAM.

On the 50 questions, the keyword floor gets Recall@5 0.98 and MRR 0.829. RAPTOR gets Recall@5 0.96, Recall@10 0.98, Recall@20 1.00, and MRR 0.861. RAPTOR ranks the right passage better, and finds every gold document by rank 20. Keyword wins Recall@5 by one question.

Two questions explain the gap. q29 reaches its gold document at rank 6. q47 reaches the first gold document at rank 14, but stays inside Recall@20. The full reference lives in mds/metrics.md in the repository.

Why local

Because the point is to see the whole pipeline. A hosted model hides the retrieval, the prompt, the judge, and the cost. A local stack lets you change one piece and rerun the same 50 questions. It also keeps the corpus on the island, which is the right default for a reserve's records.

Notes

Raptor Reserve is fictional. The bird species are real. The corpus is CC BY 4.0. The code license is separate.

Run it

The lab expects a pixi workspace named rptr, a CUDA host, and about 12 GB of VRAM.

  1. pixi install
  2. pixi run models to download the three GGUFs, then pixi run llm-up
  3. pixi run index, pixi run embed, and pixi run build-tree
  4. pixi run serve

Open http://localhost:8000. Ask and live replay need the router. Recorded replay and the keyword floor do not. The corpus can be regenerated with pixi run build-corpus.
